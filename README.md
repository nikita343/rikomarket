## Product catalog

The catalog (`data/products.json`, `lib/categories.ts`) is generated from the
original Ukrainian site `https://rikomarket.com.ua` and translated to Lithuanian.
The pipeline lives in `scripts/` and is re-runnable (the HTML cache under
`scripts/.scrape-cache/` is git-ignored):

```bash
node scripts/scrape-fetch.mjs            # 1. cache all product + category pages
node scripts/scrape-parse-categories.mjs # 2. categories-raw.json (UA hierarchy)
node scripts/scrape-parse-products.mjs   # 3. products-raw.json (UA, structured)
node scripts/scrape-inventory.mjs        # 4. (optional) list strings to translate
node scripts/metal-rondo.mjs             # 5. rebuild the metal-hose source file
node scripts/scrape-generate.mjs         # 6. write data/products.json + lib/categories.ts
node scripts/scrape-images.mjs           # 7. download images to public/products/orig/
node scripts/translate-ru.mjs            # 8. write data/products.ru.json + lib/chem-ru.ts
```

Step 6 applies the `scripts/translations-*.json` dictionaries (UA → LT) by exact
match and prints any untranslated strings. `lib/products.ts` reads the generated
JSON; `lib/categories.ts` is generated and should not be hand-edited.

Two product groups do not come from the Ukrainian scrape:

- **Armuotos PVC spirale (PVC)** — imported from polynect.com.ua
  (`scripts/scrape-polynect.mjs`). `ASPIRATO PU` is re-filed under **PUR →
  Armuotos PVC spirale** by `POLY_OVERRIDE` in the generator.
- **Metalinės žarnos** — transferred from the supplier catalogue at
  <https://rondo2.pl/katalog-produktow/weze-metalowe/> (Metalhex A / B / B1 and
  Metalhex inox C / D / D1). `scripts/metal-rondo.mjs` builds
  `scripts/metal-rondo.json` (already Lithuanian, dimension tables generated from
  one shared size list); the generator appends it and drops the old metal
  entries.

## Languages (LT + RU)

Lithuanian is the default locale and keeps the plain URLs (`/`, `/products`,
`/products/<slug>`); Russian is served from the `/ru` prefix. Each locale has its
own root layout (`app/(lt)/layout.tsx`, `app/ru/layout.tsx`, sharing
`components/SiteLayout.tsx`), so `<html lang>` and the header/footer are correct
per language; the page bodies live once in `components/pages/`.

- `lib/i18n.ts` — locale list, `localeHref()`, `splitLocale()`.
- `lib/dictionary.ts` — every interface string, per locale.
- `lib/site.ts`, `lib/industries.ts`, `lib/reference.ts`, `lib/categories.ts` —
  content with both languages side by side.
- `data/products.ru.json`, `lib/chem-ru.ts` — generated by
  `scripts/translate-ru.mjs`.

### Where the Russian wording comes from

The original site already has a Russian edition (`rikomarket.com.ua/ru/`), and it
is the authority for the technical terms. Every cached Ukrainian page carries a
`<link rel="alternate" hreflang="ru">` pointing at its Russian twin, so the two
can be matched page by page rather than by name:

```bash
node scripts/scrape-ru.mjs        # cache + parse the /ru/ pages
node scripts/scrape-generate.mjs  # category names pick up the old site's wording
node scripts/translate-ru.mjs     # rebuild the Russian catalogue
```

`scrape-ru.mjs` writes `scripts/.scrape-cache/products-ru-raw.json` (Russian
titles, description lines, tables, plus the Russian category names and the
chemical-resistance table). `translate-ru.mjs` then aligns each product's
Lithuanian lines and table cells with the Russian ones **by position** and keeps
the site's exact wording, saving what it learned to
`scripts/translations-ru-site.json`. A product is only aligned when the shapes
match exactly; anything else falls back to the hand dictionary, and the run
prints which products used which source.

The new site is the source of truth for **which products exist** and how they are
named and grouped — the import never adds, drops or re-files anything, it only
swaps text on products that are already in the catalogue. So product names keep
the catalogue's own wording, because the Lithuanian catalogue renamed several
products (Tipas B5, Tipas Flat B1 …) and the two locales should agree. Pass
`--names=site` to take the old site's headings instead.

Category names are the exception: they follow the old site's terminology
("Рукава из полихлорвинила", "Рукава типа КЛИН", "Элементы соединений"). The
scrape caches them to `scripts/.scrape-cache/categories-ru-names.json` and
`scrape-generate.mjs` writes them into `lib/categories.ts`; `CAT_RU` in that
script is the fallback for anything the old site has no page for.

`scripts/translations-ru.json` is the hand dictionary and covers what the old
site has no page for — the polynect PVC hoses and the Metalhex metal hoses. To
extend it after catalog changes, run `node scripts/i18n-extract.mjs` (it writes
the strings needing a translation to `scripts/i18n/chunks/`), merge the results
back in, and re-run `translate-ru.mjs`, which reports anything left
untranslated.

The language switch lives in the header (`components/LanguageSwitcher.tsx`) and
keeps the visitor on the same page.

## Tests

Jest + React Testing Library (configured via `next/jest`). Tests live in `__tests__/`.

```bash
npm test              # run the suite
npm run test:watch    # watch mode
npm run test:coverage # coverage report (thresholds enforced in jest.config.js)
```

- `__tests__/lib/` — unit tests for the data layer (categories, products, industries,
  reference tables, chem data, site config).
- `__tests__/components/` — component tests (unit conversion math, product cards,
  category tabs, chem-table search, header/footer, icons, ui primitives).
- `__tests__/integration/` — the full category-first ProductsBrowser flow and a
  catalog data-integrity check (products ↔ categories ↔ image assets on disk).

Coverage sits around **94% lines / 91% functions** (the `lib/` data layer is 100%).
